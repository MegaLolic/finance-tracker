# Правила данных и доставки

## Финансы и HTTP

Сервисный слой содержит бизнес-правила; DTO проверяются контроллерами, репозитории
всегда ищут финансовые записи по ID и владельцу. JWT передаёт стабильный userId;
refresh ищет пользователя по ID и берёт актуальный email. Access JWT имеет срок
10 минут, refresh — сутки. Пароли хешируются BCrypt; их длина ограничена до
хеширования. Пароли, хеши и токены исключены из строкового представления объектов,
которое используется логированием. Новый секрет HS512 — минимум 64 байта UTF-8.

При создании счёта обязательны баланс и валюта. Отрицательный баланс допустим.
Суммы операций строго положительные; INCOME увеличивает баланс, EXPENSE уменьшает.
Деньги имеют максимум 17 целых и 2 дробных знака, как PostgreSQL DECIMAL(19,2).
Обновление счёта меняет только имя: прямое изменение баланса/валюты даёт 409.
Численно одинаковые суммы `100.0` и `100.00` равны. Конвертации валют нет.
Тип существующей категории менять нельзя; используемую категорию нельзя удалить.

Счета/операции имеют `@Version`. GET/PUT возвращают версию; PUT требует текущую,
DELETE требует query `version`. Устаревшая версия — 409 без автоматического retry.
Изменение операции, баланса и outbox происходит в общей транзакции PostgreSQL:
ошибка/конфликт откатывает всё. Категории и профиль не имеют версионирования API.

Обработчики ошибок сохраняют общий JSON `status/message/errors` и стандартные
HTTP-статусы/headers Spring: неизвестный путь 404, неверный метод 405, неверный
Content-Type 415, валидация 400, авторизация 401/403, конфликт данных 409.
Finance сохраняет upstream 401/403/404; недоступность user-service — 503,
таймаут — 504, неожиданный upstream-ответ — 502. Внутренние тела ошибок не раскрываются.

## Расчёты аналитики

`AnalyticsController → AnalyticsService → RawTransactionRepository` повторяет
слои финансового сервиса. Контроллер берёт владельца из access JWT, сервис
определяет календарные границы и считает суммы через BigDecimal. Репозиторий
фильтрует по userId, accountId, deleted=false и createdAt: начало включительно,
начало дня после конечной даты исключительно. ZoneId задаёт локальные границы,
поэтому день при смене часового пояса может длиться 23 или 25 часов.
Составной индекс `(userId, accountId, deleted, createdAt)` поддерживает выборку.
Маркер deleted_users проверяется до/после чтения; при его наличии сводка пустая.

Суммы считаются по одному счёту, поскольку в проекции нет валюты. Разница доходов
и расходов не является балансом счёта. Названия категорий в проекцию не входят:
разбивка использует categoryId и categoryType. Для пустой выборки суммы/средние
равны 0.00, количества равны нулю. Категории отсортированы по ID.
Сводка строится при запросе из текущих снимков, без отдельного кеша/коллекции итогов.
Для базового объёма выбранная история счёта загружается в память; для больших
периодов потребуется потоковое чтение либо Mongo aggregation с учётом хранения
BigDecimal. Это eventual-consistent отчёт: Kafka lag влияет на свежесть,
параллельные изменения нескольких операций не дают общего SQL-снимка.

## Transactional outbox

`OutboxService` сохраняет JSON-снимок операции в `outbox_events` вместе с изменением
SQL-данных. `OutboxPublisher` берёт PostgreSQL advisory lock, выбирает старейшее
неотправленное событие каждого transaction ID и ждёт подтверждения Kafka, после
чего ставит `published_at`. Неудачная отправка повторяется и блокирует следующие
версии только этой операции. Сеть ожидается с ограниченным timeout.

Формат TransactionEvent одинаков в finance и analytics: eventId, eventType
(CREATED/UPDATED/DELETED), transactionId, version, userId, accountId, categoryId,
amount, description, categoryType, createdAt. Kafka key — transactionId. Удаление
использует последнюю entity version + 1, удаление счёта создаёт события для всех
его операций. Снимки обязательных полей проверяются до записи в MongoDB.

Доставка at-least-once: падение после Kafka ack до SQL commit может дать повтор.
MongoDB атомарно применяет только более новую версию. Удаление сохраняется как
tombstone, поэтому старые сообщения не воскрешают запись. Чтение активных данных
должно исключать `deleted=true` и удалённых пользователей.

Legacy create-сообщения без eventId/eventType/version допускаются как version=-1;
документы без версии считаются version=-2. Legacy не освобождается от проверки
содержимого. Миграция V4 ставит текущие SQL-операции в outbox для backfill, но не
может найти старые Mongo-записи операций, удалённых до появления outbox.

| Параметр | По умолчанию |
|---|---:|
| outbox.poll-interval-ms | 1000 |
| outbox.batch-size | 20 |
| outbox.send-timeout-ms | 10000 |
| outbox.retry-delay-ms | 5000 |
| outbox.retention-days | 7 |
| outbox.cleanup-batch-size | 1000 |
| outbox.cleanup-interval-ms | 3600000 |

Очистка удаляет только отправленные строки старше retention-days, не больше
batch-size за запуск, через частичный индекс и SKIP LOCKED. Первый запуск после
одного интервала. Для большого потока подстрой частоту/порцию; это не архив.
Основной transaction-events хранится 7 дней без byte cap. Analytics должен
успевать прочитать его до истечения retention. Брокер один, replica=1: volume
не заменяет резервное копирование, а восстановление аналитики из SQL — отдельная
операция, не обещанная функция автоматического восстановления.

## Удаление пользователя

User-service в одной транзакции блокирует пользователя, устанавливает deleting
и создаёт durable-запрос user_deletion_requests с requestId. API отвечает 202.
Вход/refresh/изменение профиля после начала удаления запрещены. В finance доступ
закрывается после получения Kafka-запроса, а не мгновенно в момент ответа 202.

Relay читает незавершённые запросы и повторяет отправку примерно каждые 30 секунд.
Finance и analytics используют разные consumer groups и получают запрос независимо.
Finance помечает user_lifecycle.deleted и транзакционно удаляет счета, операции,
категории и outbox пользователя. Аналитика сначала сохраняет deleted_users, затем
удаляет его документы. После локального успеха каждый сервис отправляет ack.
Только два ack с верными userId/requestId позволяют физически удалить пользователя.

Финансовые сервисные операции и удаление берут одну блокировку user_lifecycle.
Поэтому операции одного пользователя, включая чтение, последовательны; разные
пользователи не мешают друг другу. Это простой осознанный компромисс по throughput.
Сервисный метод обязан иметь userId либо валидированный TransactionFilterDto.

Standalone MongoDB не даёт общей транзакции для tombstone и документов. Listener
проверяет маркер до/после записи. Фоновая очистка обходит маркеры по ключу порциями
(user-deletion.cleanup-batch-size=100) и удаляет документы через индекс userId.
Курсор циклический, поэтому сбой между записью и проверкой исправляется позднее.
Это eventual cleanup: кратковременный документ при гонке возможен. Tombstones
сохраняются постоянно, удалённые ID повторно не используются.

## Kafka-ошибки и DLT

Analytics делает три повтора через секунду, затем переносит сообщение в
`<source>.analytics.DLT`. Producer умеет отправлять event JSON, строки ack и
исходные байты повреждённого JSON. Правильное сообщение также может попасть в DLT
при длительной недоступности MongoDB; исправь причину и выполни проверенный replay.

Координатор user-service переносит неисправимые JSON/contract-ошибки в
`user-deletion-completed.user.DLT` после ограниченных повторов. Finance переносит
такие запросы в `user-deletion-requests.finance.DLT`. Временные ошибки SQL/Kafka
в протоколе удаления повторяются, чтобы не потерять прогресс очистки. Analytics
не подтверждает запрос, который не смог очистить; durable relay пришлёт его снова.

DLT хранится 14 дней. В headers есть источник/partition/offset и причина ошибки.
Перенос считается успешным только после broker ack; при сбое DLT исходный offset
не продвигается. Между переносом и commit offset возможен дубль. DLT — карантин,
не успешная обработка, не бессрочный архив и не механизм автоматического replay.
Исторические Kafka/DLT-сообщения, логи и backups не очищаются выборочно при удалении
пользователя. Их retention — отдельное эксплуатационное правило.
